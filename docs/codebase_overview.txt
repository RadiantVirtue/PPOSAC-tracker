1. WHAT THIS PROJECT IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This is a dissertation research project investigating CREDIT ASSIGNMENT in
reinforcement learning. The central question is: when an agent succeeds or
fails at a complex hierarchical task, what structural differences appear in
the gradients that drove its learning, and do those differences explain
differences in representational quality?

Two RL algorithms are compared:
  - PPO  (Proximal Policy Optimisation) — on-policy
  - Rainbow DQN (distributional + PER + NoisyLinear + n-step) — off-policy

The environment is CRAFTER — a 64×64 pixel, procedurally-generated 2D
survival game with 22 achievements arranged in a tech-tree:
  Tier 1: collect_wood, collect_sapling, collect_drink, eat_plant, wake_up
  Tier 2: place_table, collect_stone, defeat_zombie, eat_cow,
          defeat_skeleton, make_wood_pickaxe, make_wood_sword
  Tier 3: collect_coal, place_stone, place_furnace, make_stone_pickaxe,
          make_stone_sword
  Tier 4: collect_iron, collect_diamond, make_iron_pickaxe,
          make_iron_sword, place_plant

Crafter is chosen because deep achievements (iron, diamond) require many
preparatory actions with zero immediate reward — a maximum-difficulty
credit assignment challenge.

NOTE ON THE NAME: The repo is called PPOSAC-tracker. SAC (Soft Actor-Critic)
was an earlier candidate algorithm and appears in some legacy infrastructure
(shared/tagged_buffer.py, EpisodeStore). There is NO active SAC training
code. The three live algorithms are PPO, Rainbow, and a minimal SAC stub
that was never completed. Ignore any "sac/" references — that directory
does not exist in the active codebase.

2. RESEARCH QUESTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RQ1 — Structural Gradient Signatures:
  Does the geometric differentiation of success and failure (G_uniform)
  remain directionally stable when reinterpreted through the
  trajectory-based sampling biases (G_IS) of off-policy learning?
  Metrics: gradient coherence, opposition score, gradient magnitude,
           cos(G_IS, G_uniform), all compared across checkpoints.

RQ2 — PER and Directional Influence:
  To what extent does PER dictate direction in a learning signal (rather
  than merely scaling its magnitude), and can this influence be
  empirically validated via weight-delta (Δθ) analysis?
  Metrics: cos(G_IS, G_uniform), cos(G_IS, G_reward),
           empirical validation via cos(G_IS, Δθ) vs cos(G_uniform, Δθ).

RQ3 — Representational Emergence:
  Does the directional coherence of the learning signal (G_variant)
  longitudinally predict the emergence of semantically structured
  representations in the network's penultimate layer?
  Metrics: UMAP+HDBSCAN clustering fragmentation, centroid cosine
           distance, RSA alignment score (Spearman ρ vs ground-truth
           functional RDM).

RQ4 — Moment of Reward Analysis (MORA):
  How is the learning signal distributed across the temporal phases of a
  successful trajectory (positive, neutral, and negative transitions),
  and does Rainbow's implicit credit assignment over-weight immediate
  reward feedback?
  Metrics: Moment-of-Reward sub-partitioning (r>0 vs r=0 vs r<0 within
           the success pool), per-subgroup gradient magnitude and
           coherence, cos(G_IS_r_zero, G_uniform_r_zero).

3. EPS — THE EPISODE SCORING METRIC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

EPS (Exploration Progress Score) is the primary metric for ranking episodes.

  EPS = achievements_completed + 0.9 × materials_progress

Where:
  - achievements_completed = count of achievements with truthy value
  - materials_progress = fraction of materials held toward the CLOSEST
    unachieved material-prerequisite achievement (capped per material,
    best ratio across all candidate achievements)

The 0.9 weight on materials_progress means partial progress toward the
next achievement contributes almost as much as completing a prior one —
this smooths the score to avoid ties at integer values.

PARTITIONING STRATEGY: Percentile-based (mode="percentile", percentile_x=25)
  - Bottom 25% of episodes by EPS → Failure group
  - Top 25% of episodes by EPS → Success group
  - Middle 50% DISCARDED — eliminates ambiguous episodes
  - This maximises signal contrast and defends against "mid-range pollution"

The older mode="eps" (mean-split, no discarding) is still in thresholding.py
but is no longer used in active experiments.

EPS is injected into env info by CrafterAchievementWrapper at every step.
The final EPS of an episode is whatever info["eps"] was at the terminal step.

5. ENVIRONMENT WRAPPING  (wrappers.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

crafter.Env uses the OLD gym API (4-tuple step returns). The codebase uses
gymnasium (5-tuple). Two wrapper layers bridge this:

CrafterGymnasiumWrapper(gym.Env)
  - Wraps crafter.Env
  - Converts step() from (obs, r, done, info) → (obs, r, terminated, False, info)
  - Converts reset() from obs → (obs, {})
  - Uses a seeded RNG to draw a fresh world seed per episode (reproducible
    but varied world layouts)
  - obs space: Box(0, 255, (64, 64, 3), uint8)
  - action space: Discrete(N)

CrafterAchievementWrapper(gym.Wrapper)
  - Wraps CrafterGymnasiumWrapper
  - Injects info["achievements"] = bool dict (22 achievements)
  - Injects info["eps"] = float (current EPS score)
  - Passes reward through unchanged (NO shaping)
  - IMPORTANT: Crafter's native info["achievements"] returns integer counts.
    This wrapper converts them to booleans.

make_crafter_env(seed=None) — factory, used everywhere instead of
calling crafter.Env directly.

No ImgObsWrapper anywhere. Observations remain (64, 64, 3) uint8.
PPO's SB3 NatureCNN handles normalisation internally (obs_to_tensor).
Rainbow normalises to float32 / 255.0 in agent.py.

6. PPO PIPELINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

6.1  Architecture
  Algorithm: stable-baselines3 PPO with CnnPolicy (NatureCNN feature extractor)

  Network structure (model.policy):
    features_extractor: NatureCNN
      - Conv(3→32, k8, s4) → ReLU
      - Conv(32→64, k4, s2) → ReLU
      - Conv(64→64, k3, s1) → ReLU
      - Flatten → Linear(flat→64) → ReLU   ← this is "features_extractor.linear"
    mlp_extractor:
      - policy_net: Identity (features go straight to actor head)
      - value_net:  Identity
    action_net: Linear(64 → n_actions)
    value_net:  Linear(64 → 1)

  ACTIVATION LAYER FOR ANALYSIS: "features_extractor.linear"
  Output: 64-dimensional float32 vector per observation.

6.2  Training  (ppo/train.py)
  - Uses SB3's PPO.learn() with num_envs=16 parallel environments
  - Each env seeded as seed + i*10_000
  - Checkpoints saved at fixed step intervals (checkpoint_freq, default 50k steps)
  - Achievement-triggered checkpoints: when the policy first unlocks a new
    achievement tier, an extra checkpoint is saved immediately
  - Checkpoint format: SB3 model saved via model.save() — not a raw dict.
    Load with PPO.load(path, env=env).
  - Returns log saved to logs/pporeturnlog.txt per episode

6.3  Checkpoint format
  SB3 .zip file format. Load with:
    model = PPO.load(checkpoint_path, env=env, device=device)
  The policy is then at model.policy.

6.4  Evaluation / Sampling  (ppo/sampling.py)
  collect_episodes(model, n_episodes, seed, device):
    - Runs a FROZEN policy (eval mode) for n_episodes complete episodes
    - Single env, no parallelism during evaluation
    - Returns list of EpisodeData namedtuples:
        observations: Tensor (T, H, W, C) uint8
        actions:      Tensor (T,) int64
        rewards:      Tensor (T,) float32
        dones:        Tensor (T,) float32
        eps:          float (final EPS of this episode)

  partition_episodes(episodes):
    - Calls shared/thresholding.py with mode="percentile", percentile_x=25
    - Returns (success_episodes, failure_episodes, threshold_info)

6.5  Gradient Analysis  (ppo/gradients.py)
  compute_group_gradient_with_coherence(model, episodes, batch_size, device):

  HOW IT WORKS:
    For each episode, uses SB3's policy.evaluate_actions(obs, actions) to get
    (values, log_probs, entropy). This mirrors the PPO CLIP objective.

    GAE advantages are computed:
      delta_t = r_t + γ * V_{t+1} - V_t
      A_t = delta_t + γλ * A_{t+1}    (λ=0.95, γ=0.99)
    Advantages are normalised (zero-mean, unit-std) per episode.

    Policy gradient loss: pg_loss = -(advantages * log_probs).mean()
    Backprop → accumulate ∇θ into OnlineGradientAggregator

    Episodes are processed in batches of batch_size=10 for coherence.
    Both an overall aggregator (for the mean gradient across all episodes)
    and a per-batch aggregator (for coherence computation) are maintained.

  RETURNS: (l2_normalised_mean_grad, raw_mean_grad, list_of_batch_grad_dicts)

  The list of batch grad dicts is used by shared/metrics.py coherence().

6.6  Activation Analysis  (ppo/activations.py)
  run_activation_analysis(model, success_episodes, failure_episodes, device):
    - Hooks "features_extractor.linear" on model.policy
    - Stacks all observations from both groups
    - Calls policy.obs_to_tensor() for normalisation
    - extract_activations() runs all obs through the network in batches of 256
    - UMAP (2D projection) + HDBSCAN (clustering) on the result
    - Computes centroids for success/failure groups
    Returns dict with: activations, projected, cluster_stats, centroids, labels

7. RAINBOW PIPELINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

7.1  Architecture  (rainbow/model.py)
  Full Rainbow DQN components:
    - Distributional value (C51): 51 atoms, V_min=-10, V_max=10, Δz=0.4
    - Double Q-learning (online + target networks)
    - Dueling architecture (value stream + advantage stream)
    - NoisyLinear (replaces ε-greedy; σ₀=0.1)
    - Prioritized Experience Replay (PER)
    - N-step returns (n=3)

  Network structure (DQN, "canonical" architecture):
    convs: Sequential(
      Conv(3→32, k8, s4), ReLU,
      Conv(32→64, k4, s2), ReLU,
      Conv(64→64, k3, s1), ReLU,
      Flatten()
    )   ← output is (B, 1024) after flatten for 64×64 input
    fc_h_v: NoisyLinear(1024 → hidden_size)   ← value stream
    fc_h_a: NoisyLinear(1024 → hidden_size)   ← advantage stream
    fc_z_v: NoisyLinear(hidden_size → atoms)
    fc_z_a: NoisyLinear(hidden_size → atoms × n_actions)

  Forward pass output: log-probabilities over (atoms × n_actions) → Q-value
  distribution per action.

  ACTIVATION LAYER FOR ANALYSIS: "convs"
  Output shape BEFORE flatten: (B, 64, 4, 4) for 64×64 input.
  flatten_output=True in extract_activations() converts this to (B, 1024).
  So effective analysis dimension = 1024.

  NoisyLinear eval mode: in eval(), NoisyLinear uses only μ weights (no
  noise sampled). The σ parameters receive zero analytical gradient in eval
  mode. This is important for weight-delta analysis (see section 7.7).

  Input normalisation: raw uint8 obs are divided by 255.0 to float32 in
  agent.py. History_length=3 corresponds to RGB channels, NOT temporal
  stacking. Replay history is effectively 1.

7.2  Agent  (rainbow/agent.py)
  DQNAgent wraps the DQN model with:
    - act(obs, eval_mode): epsilon=0 in eval; NoisyLinear provides exploration
    - learn(memory, batch): distributional Bellman update with IS weights
    - save/load_checkpoint(): saves both online_net and target_net

  Checkpoint format (dict, not SB3 zip):
    {
      "global_step":           int,
      "episode_count":         int,
      "online_net_state_dict": OrderedDict,
      "target_net_state_dict": OrderedDict,
      "optimizer_state_dict":  dict,
      "args_dict":             dict  (all hyperparameters)
    }

  IMPORTANT: Both online AND target networks are saved. The target net is
  needed for offline distributional Bellman loss reconstruction during
  gradient analysis (see section 7.5).

7.3  Replay Memory  (rainbow/memory.py)
  PrioritizedReplayMemory uses a SumTree for O(log N) priority sampling.
    - Capacity: 500K transitions (default)
    - PER exponent α=0.5: priority = TD_error^α
    - IS exponent β: annealed from 0.4 to 1.0 over T_max steps
    - N-step return buffer: accumulates n=3 steps before storing

  The live replay buffer is NOT saved with checkpoints (too large). Only the
  model weights and args are checkpointed. This is the core problem that
  motivates the analytical IS weight reconstruction (see section 7.5).

7.4  Training  (rainbow/train.py)
  - Single environment (no parallel envs during training for Rainbow)
  - Observations normalised to float32 / 255.0
  - Two checkpoint pointers maintained simultaneously:
      "live" checkpoint: overwritten each time — used for training resumption
      "analysis" checkpoint: timestamped files — used for offline analysis
    This keeps disk use manageable without losing analysis checkpoints.
  - Target network hard-copied every target_update=8000 steps
  - Minimum replay size before learning begins: min_replay_size=5000
  - Checkpoint interval: checkpoint_interval steps (default 50k)

7.5  Gradient Analysis  (rainbow/gradients.py)
  This is the most complex part of the codebase. Read carefully.

  PROBLEM: The live PER priority queue is not saved with checkpoints. So
  when we later do offline analysis, we cannot recover the exact IS weights
  that would have been assigned to each transition during training.

  SOLUTION: Analytically reconstruct IS weights from the frozen network.
    1. For each transition (s, a, r, s'), compute the distributional
       Bellman loss using the SAVED online_net and target_net.
    2. Use that loss as a proxy for the original TD error.
    3. Apply priority = loss^α (same α as training).
    4. Normalize: w_i = (priority_i / sum(all_priorities))^(-β)
       where β = β_schedule(global_step) and sum is over the JOINT pool
       of success + failure transitions (joint normalization, see below).
    5. Rescale so max weight = 1.0.

  THREE GRADIENT VARIANTS computed per group (success / failure):
    G_uniform:  unweighted mean gradient (baseline)
    G_IS:       IS-weighted mean gradient (principled PER correction)
    G_reward:   |reward|-weighted gradient (independent proxy, |r|+ε weight)

  WHY JOINT IS NORMALIZATION (v5):
    If we normalize IS weights separately per group, the denominators are
    different, making gradient magnitudes incomparable across groups. By
    pooling success + failure together for the normalization step, the IS
    weights have the same scale, and cosine magnitudes become
    cross-comparable. A residual bias remains (IS upweights low-error
    transitions, and low-error is correlated with success), but the
    directional comparison is now valid.

  THREE-PASS DESIGN:
    Pass 0 (no_grad): Forward all transitions through the frozen network
                      to compute per-transition losses → IS weights.
    Pass 1a:          Backward with uniform weights → G_uniform
    Pass 1b:          Backward with IS weights → G_IS   (retain_graph=True)
    Pass 1c:          Backward with reward weights → G_reward

  retain_graph=True is necessary because the same computation graph is
  reused for three backward passes.

  compute_group_gradient_with_coherence(online_net, target_net, episodes,
                                        global_step, args, device):
    Returns dict with keys:
      "uniform_l2", "is_l2", "reward_l2"          — normalised mean grads
      "uniform_raw", "is_raw", "reward_raw"        — raw mean grads
      "uniform_batch_grads", ...                   — per-batch grad lists
      "cos_is_uniform", "cos_is_reward"            — diagnostic cosines
      "is_weights_summary"                         — weight stats

7.6  Activation Analysis  (rainbow/activations.py)
  run_activation_analysis(model, success_episodes, failure_episodes, device):
    - Hooks "convs" on DQN
    - Uses flatten_output=True (4D conv output → 1024-dim)
    - Otherwise identical pipeline to PPO: UMAP + HDBSCAN + centroids
    - Observations must be (T, 3, H, W) float32 in [0,1] (already normalised)

7.7  Weight-Delta Validation  (rainbow/weight_delta.py)
  PURPOSE: Validate that the analytically reconstructed IS gradients
  actually align better with real training dynamics than the naive uniform
  gradients.

  METHOD:
    1. Load two consecutive checkpoints: θ_N and θ_{N+1}
    2. Compute Δθ = θ_{N+1} - θ_N (actual parameter movement)
    3. Compute offline gradients at checkpoint N (G_uniform, G_IS, G_reward)
    4. Compute cos(G_variant, Δθ) for each variant

  If cos(G_IS, Δθ) > cos(G_uniform, Δθ), IS reconstruction is
  directionally validated. Absolute cosine values will be LOW (close to
  zero) due to Adam momentum, learning rate schedule, and temporal
  mismatch between offline gradient computation and live training. Only
  the RELATIVE ORDERING matters.

  NoisyLinear σ EXCLUSION:
    σ parameters have zero analytical gradient in eval mode (noise not
    sampled during forward pass). But they DO receive real training updates.
    They must be EXCLUDED from both Δθ and the gradient dicts to ensure
    structural comparability. weight_delta.py handles this explicitly.

  TIMING: Most informative at MID-TRAINING when Δθ is largest (early
  training has big moves but noisy; late training has tiny Δθ, near-zero
  cosines everywhere).

7.8  Moment of Reward  (rainbow/moment_of_reward.py)
  PURPOSE: Test RQ2 — does PER implicitly over-weight immediate-reward
  transitions over preparatory zero-reward transitions?

  METHOD:
    Take the SUCCESS pool only (high-EPS episodes).
    Sub-partition transitions by reward sign:
      r_pos: transitions with reward > 0    (achievement unlocks)
      r_zero: transitions with reward == 0  (preparatory subtasks)
      r_neg: transitions with reward < 0    (death / starvation)

    Compute G_uniform and G_IS for each sub-partition.
    Compare:
      - gradient magnitudes (do achievement frames dominate?)
      - gradient coherence (are their signals consistent?)
      - opposition score between r_pos and r_zero gradients
        (do they point in opposite directions? same direction?)

    cos(G_IS_r_zero, G_uniform_r_zero) is the KEY diagnostic:
      high cosine → IS correction doesn't change zero-reward gradient
                    direction much → PER was already weighting these fairly
      low cosine → IS correction substantially shifts direction →
                   PER was biasing against preparatory transitions

    15 metrics total per checkpoint. Plotting suite in the same file.

7.9  Sampling  (rainbow/sampling.py)
  collect_episodes(agent, n_episodes, seed, device):
    - Runs frozen Rainbow policy for n_episodes
    - Single env during evaluation
    - Returns list of EpisodeData:
        observations: Tensor (T, 3, H, W) float32 in [0,1]
        actions:      Tensor (T,) int64
        rewards:      Tensor (T,) float32

8.1  shared/achievements.py
  Defines the 22 Crafter achievements and their properties.

  CRAFTER_ACHIEVEMENTS — ordered list of achievement names (use this for
    indexing, ordering, and iterating)

  CRAFTER_ACHIEVEMENT_REWARDS — per-achievement shaped reward values.
    NOT used in training (rewards come from crafter.Env directly). Used
    only for documentation / analysis weighting.

  ACHIEVEMENT_MATERIALS — material prerequisites per achievement (e.g.
    make_stone_pickaxe requires stone=3). Used by compute_materials_fraction.

  compute_materials_fraction(achievements_dict, inventory) → float [0,1]
    Returns the fraction of materials held toward the closest unachieved
    material-gated achievement. Used to compute the materials_progress
    component of EPS.

  compute_eps(achievements_completed, materials_progress) → float
    EPS = achievements_completed + 0.9 * materials_progress

  count_achievements(achievements_dict) → int
    Count of achievements with truthy value.

8.2  shared/metrics.py
  All scalar metrics for analysis outputs.

  opposition_score(grad_success, grad_failure) → float [-1, 1]
    Cosine similarity between the mean success and mean failure gradients.
    -1 = perfectly opposite (ideal), 0 = orthogonal, +1 = same direction.
    NOTE: +1 is NOT automatically bad. If success and failure involve
    different behaviours (not just different intensities of the same
    behaviour), orthogonal gradients (~0) are expected and meaningful.
    Coherence disambiguates.

  coherence(minibatch_gradients) → float [-1, 1]
    Mean pairwise cosine similarity within a list of per-episode gradient
    dicts. High coherence means episodes in the group produced similar
    gradient updates — consistent credit signal.

  gradient_magnitude(mean_gradient) → float
    L2 norm of the concatenated mean gradient vector.

  activation_separation(centroid_success, centroid_failure) → float
    Euclidean distance between group centroids in activation space.

  centroid_cosine_distance(centroid_success, centroid_failure) → float
    1 - cosine_similarity between centroids. Preferred over Euclidean
    for cross-algorithm comparisons (PPO 64-dim vs Rainbow 1024-dim).

  rsa_alignment(model_rdm, ground_truth_rdm) → dict{"correlation", "p_value"}
    Spearman ρ between upper triangles of two RDMs.

8.3  shared/gradient_utils.py
  OnlineGradientAggregator
    Accumulates gradients online without storing individual episode vectors.
    Avoids OOM when processing thousands of episodes.

    __init__(named_params): initialises sum_grads dict (zeros)
    accumulate(named_params): adds current .grad values to running sum
    mean_gradient(): returns {name: sum/count} dict
    l2_normalized(): returns L2-normalised mean gradient dict

  cosine_similarity_flat(grads_a, grads_b) → float
    Concatenates all layers alphabetically, computes single cosine.
    Used for opposition score and weight-delta comparisons.

  cosine_similarity_layerwise(grads_a, grads_b) → {name: float}
    Per-layer cosine similarities. Used for layer-level diagnostics.

8.4  shared/thresholding.py
  partition_episodes(episodes, scores, mode="eps", percentile_x=25):
    mode="percentile" (ACTIVE):
      - Sorts by score, takes bottom percentile_x% as failure,
        top percentile_x% as success, discards middle.
      - Returns (success, failure, (lower_cutoff, upper_cutoff))

    mode="eps" (LEGACY, not used in active experiments):
      - Mean split, no discarding.
      - Returns (success, failure, mean_eps)

8.5  shared/rsa.py
  Full RSA pipeline for PPO (and extensible to Rainbow).

  STIMULUS SET:
    Resources: Wood, Stone, Iron, Coal  (from collect_* achievements)
    Threats:   Zombie, Skeleton          (from defeat_* achievements)
    Tools:     Wood Pickaxe, Stone Pickaxe, Iron Pickaxe
    (Lava excluded: no achievement signal; Diamond excluded: too rare)

  STIMULUS DETECTION: The observation frame at which an achievement is
  FIRST unlocked within an episode is used as the representative stimulus
  frame. This is read from info["achievements"] at each step — no
  privileged information. Only stimuli achieved at least once have data.

  FUNCTIONAL GROUPS (ground-truth RDM):
    Resources → same group; Threats → same group; Tools → same group
    Cross-group dissimilarity = 1.0, within-group = 0.0

  run_rsa(policy, episodes_with_transitions, layer_name, device):
    1. Collect stimulus frames per achievement label
    2. Compute mean activation for each label's frame set
    3. Build cosine dissimilarity RDM (n×n matrix)
    4. Compute Spearman ρ between model RDM and functional-group RDM
    Returns: {rdm, labels, alignment_score, n_stimuli, n_frames}

  NOTE: RSA is currently implemented only for PPO. The pipeline uses
  policy.obs_to_tensor() which is SB3-specific.

8.6  shared/activation_utils.py
  extract_activations(model, observations, layer_name, device,
                      flatten_output=False) → np.ndarray (N, D)
    Registers a forward hook on the named layer, runs all observations
    through the network in batches of 256, returns collected activations.
    flatten_output=True needed for Rainbow's "convs" layer (4D → 2D).
    model.named_modules() is used to look up the layer by name.

  reduce_dimensions(activations, method="umap") → np.ndarray (N, 2)
    UMAP or t-SNE projection to 2D. UMAP params: n_components=2,
    random_state=42.

  cluster_activations(projected, labels) → dict
    HDBSCAN(min_cluster_size=15) clustering on 2D projections.
    Returns: {n_clusters, noise_fraction, clusters: [{success_count,
              failure_count, size}]}

  compute_centroids(activations, labels) → {"success": np.ndarray,
                                            "failure": np.ndarray}
    Mean activation vector per group (labels: 1=success, 0=failure).

9.1  analyze_checkpoint.py  (main entry point for offline analysis)
  Runs the complete analysis pipeline for a single checkpoint.
  Called by the training scripts after each checkpoint is saved.
  Can also be invoked standalone for debugging/reanalysis.

  Pipeline for PPO checkpoint:
    1. Load model (PPO.load)
    2. collect_episodes → partition_episodes → success/failure groups
    3. compute_group_gradient_with_coherence for each group
    4. run_activation_analysis
    5. run_rsa (using achievement-unlock frames from collected episodes)
    6. Compute all metrics (opposition, coherence, magnitude, separation,
       cosine distance, RSA alignment)
    7. save_analysis_results → analysis_logs/ppo/<step>.json

  Pipeline for Rainbow checkpoint:
    1. Load online_net + target_net from checkpoint dict
    2. collect_episodes → partition_episodes
    3. compute_group_gradient_with_coherence (3 variants)
    4. run_activation_analysis
    5. run_moment_of_reward (success pool sub-partitioned by reward sign)
    6. run_weight_delta (if consecutive checkpoint available)
    7. Compute all metrics
    8. save_analysis_results → analysis_logs/rainbow/<step>.json

9.2  analyze_range.py
  Iterates over a range of checkpoint files and calls analyze_checkpoint.py
  for each. Used for batch reanalysis of existing checkpoints.

9.3  train_and_analyze.py  (top-level CLI)

  Uses tyro for argument parsing with dataclass-based config.

  Key shared parameters:
    seeds: list of random seeds to run (default [1,2,3,4,5])
    n_eval_episodes: episodes to collect per checkpoint analysis (default 1000)
    split_mode: "percentile" (active) or "eps" (legacy)
    percentile_x: percentile cutoff (default 25)
    analyze_every: run analysis every N checkpoints (default 1)
    device: "cuda" or "cpu"

12. KEY DESIGN DECISIONS AND THEIR RATIONALE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

12.1  Why percentile partitioning (not mean-split)?
  Mean-split includes borderline episodes where the agent did "medium" —
  these pollute both groups with ambiguous credit signals. Top/bottom 25%
  with middle 50% discarded guarantees contrast between groups.

12.2  Why IS weights reconstructed analytically (not read from buffer)?
  The PER priority queue is a live data structure that changes with every
  training step. It cannot be cheaply serialised (it's a 500K-entry SumTree).
  The analytical reconstruction uses the frozen network's distributional
  Bellman loss as a post-hoc proxy for TD error. This is justified in
  docs/PER_GRADIENT_BIAS.md. Accuracy is validated by weight_delta.py.

12.3  Why joint IS normalisation (v5 change)?
  Separate normalisation per group makes gradient MAGNITUDES incomparable
  across groups. Joint normalisation (success+failure in one pool) aligns
  the denominators so that "success gradient is larger than failure gradient"
  is a meaningful statement after IS weighting.

12.4  Why L2-normalise gradients before cosine comparisons?
  Policy gradient loss (PPO) and distributional Bellman loss (Rainbow) have
  incompatible scales. Normalising before cosine operations removes magnitude
  from the comparison, leaving only directional information — which is what
  coherence and opposition measure.

12.5  Why cosine distance (not Euclidean) for activation comparisons?
  PPO produces 64-dim activations; Rainbow produces 1024-dim. Euclidean
  distance scales with dimensionality in ways that make cross-algorithm
  comparisons invalid. Cosine distance is dimension-invariant.

12.6  Why exclude NoisyLinear σ from weight-delta?
  σ parameters have analytical gradient = 0 in eval mode (noise not
  sampled during forward pass). The gradient dict contains zero for these
  params. But σ does receive real updates during training (it controls
  exploration noise magnitude). Including it would artificially deflate
  cosine similarity between gradients and Δθ. Excluding it gives a fair
  comparison over parameters that actually appear in both signals.

12.7  Why retain_graph=True in Rainbow gradient computation?
  Three backward passes share the same computation graph (same forward pass
  through the frozen network). Without retain_graph=True, PyTorch frees
  the graph after the first backward, causing an error on the second. The
  graph is freed only after all three passes complete.

12.8  Why track both opposition score AND coherence?
  Opposition ≈ 0 is ambiguous: it could mean the model makes NO distinction
  between success and failure episodes (bad), OR it could mean success
  and failure episodes involve structurally DIFFERENT behaviours that happen
  to produce orthogonal gradients (informative). High coherence within each
  group disambiguates: if episodes in the success group are consistent with
  each other but differ from failure episodes, the agent has learned real
  structure even if opposition ≈ 0.

12.9  Why use the frame of first achievement unlock for RSA stimuli?
  This is the first moment the agent received the achievement signal — the
  observation most directly associated with that achievement in the
  environment. Using later frames would include noise. Using "any frame
  with the item present" would require privileged state access not available
  from env.step() info.

14. PITFALLS AND GOTCHAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- PPO observations: (T, H, W, C) uint8, channels LAST. Pass through
  policy.obs_to_tensor() before feeding to the network. Do NOT manually
  permute or normalise — SB3 handles it.

- Rainbow observations: (T, C, H, W) float32 in [0,1], channels FIRST.
  Already normalised in EpisodeData. Pass directly to the network.

- The "convs" hook on Rainbow returns a 4D tensor (B, 64, 4, 4).
  Always pass flatten_output=True to extract_activations() when hooking
  "convs". Forgetting this causes shape errors downstream.

- shared/networks.py is EMPTY (just a comment). Do not import ACModelWrapper
  from it — it does not exist. The file is kept only to not break legacy
  imports.

- shared/tagged_buffer.py (EpisodeStore) is UNUSED in active code. It was
  designed for SAC. Do not attempt to use it — there is no active SAC
  pipeline.

- Checkpoint loading for PPO: use PPO.load(path, env=env) not torch.load().
  SB3 uses a zip format; torch.load will fail.

- Checkpoint loading for Rainbow: use torch.load(path) and access keys
  "online_net_state_dict" and "target_net_state_dict". The args dict is
  at key "args_dict".

- Rainbow's history_length=3 is RGB CHANNELS, not temporal depth. The
  replay buffer stores single frames, not frame stacks. Do not assume
  temporal stacking.

- IS weight validation (weight_delta.py) gives low ABSOLUTE cosine values
  due to Adam. Never interpret cos ≈ 0.05 as "no alignment". The meaningful
  comparison is cos(G_IS, Δθ) vs cos(G_uniform, Δθ) — the relative
  improvement of IS over baseline.

- Achievement rewards in shared/achievements.py are NOT used during
  training. Crafter provides its own reward signal internally. The dict is
  documentation only.

- The experiment output directory (ppo_experiment_root/) is gitignored or
  large. Do not assume it is present on a fresh clone.
